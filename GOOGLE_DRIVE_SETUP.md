# Google Drive: синхронизация sBoard и настройка OAuth

## Как устроена синхронизация

- Используется Google Drive API v3 и скрытая папка приложения **appDataFolder** (scope `drive.appdata`).
  Файлы в ней не видны в обычном интерфейсе Drive и доступны только этому приложению.
- В аккаунте хранится **один** файл `sboard_backup.enc`. Каждая синхронизация обновляет его на месте
  (`PATCH …/upload/drive/v3/files/{id}`); новые копии не создаются. Случайные дубликаты (два устройства
  создали файл одновременно) сливаются в основной файл и удаляются.
- Формат файла (`BackupFormat.kt`):
  `SBOARDv2 | header JSON | IV | тело | SHA-256`.
  Заголовок открыт, но аутентифицирован: id хранилища, номер поколения, обёртки ключа
  (Argon2id(мастер-пароль) → AES-256-GCM и, если создан, Recovery Key). Тело — gzip(JSON) с
  записями, каждая из которых уже зашифрована ключом хранилища, — дополнительно шифруется
  AES-256-GCM подключом HKDF(ключ хранилища) с заголовком в качестве AAD.
- Проверки целостности: MD5 Drive после загрузки, SHA-256 всего файла до расшифровки, GCM-тег
  тела и каждой записи. Повреждённая или подменённая копия **никогда не перезаписывается
  автоматически** — пользователь видит предупреждение и может вручную заменить облачную копию.
- Слияние трёхстороннее по каждой записи (`SyncMerger.kt`): базой служит хэш версии, последней
  подтверждённой в Drive. Изменения с одной стороны применяются, при изменении с обеих сторон
  побеждает более новая версия (правка сильнее удаления), проигравшая сохраняется в истории записи.
  Удаления распространяются через аутентифицированные tombstone-записи (хранятся 180 дней).
- Конкурентная запись: перед загрузкой проверяется `version` файла в Drive; если другое устройство
  успело записать, цикл «скачать → слить → загрузить» повторяется.
- Без сети изменения остаются в локальной базе с отметкой «ожидает отправки»; WorkManager
  запускает синхронизацию при появлении сети (экспоненциальная задержка), после разблокировки,
  при открытии приложения и раз в час.
- Синхронизация выполняется только когда хранилище разблокировано: ключ хранилища существует
  только в памяти. Если устройство заблокировано, задача ждёт следующей разблокировки.
- Смена мастер-пароля распространяется на другие устройства (обновляются обёртки ключа, записи не
  перешифровываются). Биометрия остаётся локальной для каждого устройства.
- Устройства перечислены в зашифрованном теле файла; устройство можно отключить из Профиля →
  Устройства — при следующей синхронизации оно отключит Google на своей стороне.

## Сценарий «второе устройство»

1. Установите sBoard → «Восстановить из Google Drive».
2. Войдите в тот же аккаунт Google — приложение найдёт `sboard_backup.enc`.
3. Введите мастер-пароль (или Recovery Key). Ключ расшифровывается только на устройстве.
4. Хранилище восстановлено и разблокировано; дальше изменения синхронизируются автоматически.

Если на втором устройстве уже создано своё хранилище, Профиль → Синхронизация предложит
**объединить** его с облачным (записи перешифровываются ключом облачного хранилища) или
**заменить** облачную копию.

## Что нужно сделать владельцу проекта (без этого вход в Google не заработает)

sBoard не содержит фиктивных ключей. Для Android-клиента OAuth секрет в APK не нужен — Google
проверяет пару «package name + SHA-1 сертификата подписи».

1. Google Cloud Console → создайте проект (или используйте существующий).
2. **APIs & Services → Library → Google Drive API → Enable.**
3. **OAuth consent screen / Branding**: тип External, название sBoard, e-mail поддержки; добавьте scopes
   `.../auth/drive.appdata`, `.../auth/userinfo.email`, `.../auth/userinfo.profile`.
   Пока приложение в режиме *Testing*, добавьте свои аккаунты в **Test users**.
4. **Credentials → Create credentials → OAuth client ID → Android**:
   - Package name: `com.sboard.app`
   - SHA-1: отпечаток ключа, которым подписан **установленный** APK.
     Локально: `./gradlew :app:signingReport` или
     `keytool -list -v -keystore <keystore.jks> -alias <alias>`.
   Создайте отдельный Android-клиент для debug-ключа и для release-ключа.
5. Для стабильного SHA-1 в GitHub Actions добавьте секреты репозитория:
   `SBOARD_KEYSTORE_BASE64` (keystore в base64), `SBOARD_KEYSTORE_PASSWORD`, `SBOARD_KEY_ALIAS`,
   `SBOARD_KEY_PASSWORD`. Тогда release-APK подписывается постоянным ключом; без них собирается
   неподписанный `app-release-unsigned.apk`. Debug-APK из CI подписывается временным ключом раннера,
   и его SHA-1 меняется — для проверки входа используйте локальную сборку или release.
6. На устройстве должны быть Google Play services и вход в Google-аккаунт.

Web client ID и серверная часть не требуются: токен доступа выдаётся `AuthorizationClient`
на устройстве, sBoard его не сохраняет (Google Play services кэширует только сам грант).

Типичные ошибки: `DEVELOPER_ERROR (10)` — не совпадает package name/SHA-1 или клиент не создан;
`accessNotConfigured` — не включён Drive API; `insufficientPermissions` — пользователь не выдал
доступ к данным приложения.
